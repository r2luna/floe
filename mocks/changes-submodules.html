O1 — submodule as a repo row in the tree recommended

A submodule is a folder that happens to be a repo, so it takes the folder row: chevron, name, file count, +/− rollup. It adds a branch glyph before the name and, on the right, what the superproject sees: the branch it is on and how far it moved from the recorded commit. Nested submodules nest the same way, at any depth. h/l fold it like any folder.

What the row says

  • name — the submodule path relative to its parent repo, not to the superproject. packages/ui, not app/packages/ui: it sits under app, the nesting already says the rest.
  • ref — the branch the submodule checkout is on (or the short SHA when detached), then one of: dirty (working tree changes), +N commits (HEAD moved past the commit the parent records, amber), clean. The pointer-only case shows recorded → HEAD and no branch, because "which branch" is not the question there.
  • count / +− — roll up the files in that repo including its own submodules, exactly like a folder rolls up its children.
  • a moved pointer with a clean tree is still a change in the parent (git's M packages/brain), so the row shows with count 0 rather than disappearing. Landing on it opens the parent's gitlink diff: -Subproject commit 3f1c2a9 / +Subproject commit 9b56b50.
  • keyboard — h/l fold and unfold like a folder, o opens the file in the OS, and the diff beside the list is run inside the submodule's own repo (git -C app diff …). Folded state persists per worktree like folders do.
  • header — 13 files · 3 repos so an all-clean superproject with a dirty submodule never reads as "No changes." again.
  • files panel and palette — the same walk feeds them: the file search indexes every submodule's tree, and the files tree shows the same repo row where a submodule starts. Out of scope for this mock, same data.
